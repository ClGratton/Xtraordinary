# Android UI audit — 2026-08-11

Status: baseline captured before the Settings and onboarding corrections in this change.

## Scope and method

This audit reviews the checked-in 412 x 915 dp screenshot references, compact-height and 1.3x font-scale setup references, the Compose source for Focus, Read, Tools, passes, device management, Settings, and first-run setup, plus the product and design authorities in `PRODUCT.md` and `DESIGN.md`.

The review uses five equal dimensions (0–4 each): information architecture, hierarchy and visual craft, interaction and state clarity, accessibility and adaptive behavior, and product trust. Priority levels are P0 blocking, P1 high, P2 medium, and P3 polish.

## Findings

### P1 — Google backup is owned by the wrong flow

Location: `SettingsSheetContent`, first-run Welcome page, and `MainActivity` authorization wiring.

The disconnected Settings state says “Run setup again to opt in” even though the same surface already receives the Google authorization callback. An optional account integration must be connectable, reconnectable, synchronized, and removable from Settings without replaying onboarding. Setup may offer the option once, but it cannot become the management surface.

Action: add a direct Connect with Google action to Settings, keep explicit consent and legal links adjacent to that action, and retain Sync now plus Delete and disconnect for a connected account.

### P1 — Setup page one combines orientation with a dense legal/account task

Location: first-run Welcome screenshot and `WelcomeSetupPage`.

The first page is visually dominated by an optional backup consent card. This weakens the value proposition and makes the primary path appear blocked until a checkbox is accepted, even though setup is skippable. It also produces a tall scroll region whose continuation is not obvious on compact devices.

Action: keep Google backup optional and self-contained, reduce its hierarchy below the product introduction, use a clear direct action, and preserve scrolling for large text rather than hiding content. The onboarding illustration must communicate the phone-to-XTEINK relationship instead of repeating a generic device outline.

### P1 — Responsive coverage does not yet match the UI density

Locations: Setup, Settings, Read filter row, pass mode controls, and planned Tools grid.

The app has a compact-height setup reference and one large-text reference, but Settings is only captured at default font scale and its screenshot ends midway through Controls. Read places three selectors in one horizontal row. Pass mode controls use unequal columns with long supporting copy. These are likely failure points at 1.3x font scale, narrow widths, and translated strings.

Action: add Settings disconnected/connected and large-text references; define adaptive wrapping or vertical fallback for dense rows; require compact/default/large-text evidence for every changed full-screen or sheet surface.

### P2 — Settings has weak section prioritization

Location: `SettingsSheetContent`.

Appearance, four Bluetooth policies, reader refresh, controls, reading statistics, Google backup, legal links, and setup replay form one long undifferentiated scroll. Frequent user/account actions are below expert device tuning. The sheet title and close action consume a full row while the device-policy content begins immediately below.

Action: order sections by expected use and product context: appearance, device behavior, reading, then low-frequency backup and setup/help actions. Keep Google backup immediately before setup replay so it remains independently manageable without being promoted above common preferences. Group expert radio values into a clearly labeled device-behavior section and keep applied/pending state beside that group.

### P2 — Planned tools look actionable

Location: Tools hub.

“Planned” is visible, but large filled cards, icons, and parity with available tools imply that each card can be opened. This increases noise and makes the product feel like a roadmap grid rather than a focused companion.

Action: retain the roadmap if desired, but visually subordinate or collapse planned items and ensure their semantics do not announce them as enabled buttons.

### P2 — Read controls prioritize implementation categories over scanning

Location: Read library.

The folder action, large search field, three filters, book cards, services reminder, and floating import action compete above the fold. The three-filter row will be fragile under font scaling. Raw X3 paths use saturated accent color and can dominate book metadata.

Action: keep search primary, move secondary filters into an adaptive flow or one filter affordance on compact widths, and treat paths as tertiary metadata with truncation.

### P2 — Some status guidance is separated from the disabled action

Location: firmware install and other device-state sheets.

The firmware action says “Turn on or wake X3,” while cable guidance appears as a separate paragraph below. The improved loading copy is directionally correct, but action eligibility, current phase, and the physical instruction should remain one coherent state block and be announced to accessibility services.

Action: use a reusable operation-state pattern: current phase, one physical instruction, progress, then recoverable action.

### P3 — Icon and illustration language was inconsistent

Locations: onboarding, Tools, device status, and Focus preview.

Focus uses rich monochrome editorial imagery, while the original onboarding placeholders were bare Canvas outlines and Tools mixes symbols with different visual weights. The onboarding correction deliberately stays closer to the quiet placeholder grammar instead of importing the sophisticated Focus illustration style into a small instructional icon.

Resolution: use a coordinated transparent PNG base set with flat navy/lavender/coral geometry, a generic Android hole-punch phone with no iPhone cues, and the established 176 × 150 dp footprint. Keep functional controls as vectors. Add restrained Compose-native motion that explains each step: sequential transfer dots, books filing into a folder, and outward signal pulses. Animate only the active page and freeze previews for deterministic evidence.

## What is already working

- The permanent Focus/Read/Tools hierarchy is understandable and consistent.
- Focus has one dominant state object, strong numerical hierarchy, and an explicit start action.
- Device and firmware surfaces generally avoid claiming success before protocol evidence.
- Expressive and Quiet preserve the same structure rather than becoming separate products.
- Core touch targets are large and the palette has strong foreground/background separation.
- The cloud copy clearly limits backup to reading data and keeps books and passes local.

## Acceptance criteria for the correction

1. A disconnected user can start Google authorization directly in Settings without reopening setup.
2. Connected, disconnected, syncing, authorization-error, deletion, and legal states remain understandable in the same Settings section.
3. Setup retains its three-page structure and current illustration footprint, but each page uses a coherent finished PNG rather than a generic placeholder drawing.
4. Default, compact-height, and 1.3x text renders expose all required actions through visible layout or ordinary scrolling, without a hidden “more” affordance.
5. A machine-checked repository policy requires the UI decision workflow document and the screenshot evidence contract.
