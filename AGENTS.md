# Xtraordinary engineering guidance

- Every milestone task must read `TODO.md` first as the authoritative actionable backlog, then read only the directly relevant current `HANDOFF.md` section and its linked policy or evidence files. Older unchecked tracker entries are incident history unless represented in `TODO.md`. Update `TODO.md` status at the milestone checkpoint.
- Design for maintenance: before adding a feature-specific command, state flag, timeout, or UI rule, identify the reusable lifecycle or policy primitive and implement the feature through it. Keep validation and dependent-option logic centralized so new values do not require copied conditionals.
- Preserve Bluetooth bonding and pairing data during builds, flashes, and diagnostics unless the user explicitly requests a bond reset.
- Do not report that a wireless-debug phone is absent after only `adb devices`. A sandbox-started ADB daemon can be network-blocked even when later clients run outside the sandbox. When wireless debugging is expected, use `scripts/resolve-xtraordinary-deployment-targets.ps1`: it checks an existing authenticated device first, then when OpenScreen has no current `_adb-tls-connect._tcp` service restarts the normal-user repository daemon with `ADB_MDNS_OPENSCREEN=0` to probe Windows Bonjour, connects only a freshly discovered endpoint, and reruns `adb devices -l` before declaring the phone unavailable. Never expose a pairing code.
- Do not report X3 absent from a serial-port list alone. `scripts/resolve-xtraordinary-deployment-targets.ps1` must first inspect present `VID_303A:1001` composite and interface PnP records, then select the associated serial interface; preserve NVS, bonds, app data, and SD/books during all discovery.
- Build Android only through `scripts/build-xtraordinary-app.ps1`; it resolves the repository root and activates the checked-in toolchain paths, so callers must not guess a working directory.
- Build X3 firmware only through `scripts/build-x3-firmware.ps1`, outside the sandbox, and never concurrently with Gradle. Direct sandboxed PlatformIO compiler children consistently fail on Windows with error 5.
- Before any X3 application flash, resolve the selected OTA application partition through the shared slot policy. Android must require a live `RUNTIME_TRACE_OTA` record whose running and next-boot partitions match; the guarded Windows flasher must read and CRC-validate `otadata` before writing. Never assume `app0`/`0x10000`, never rewrite `otadata` in the raw application-only workflow, and fail closed when selection is missing, invalid, aborted, contradictory, or unsupported. `otadata` proves the selected boot target, not the firmware that ultimately ran after fallback; accept the running version only from a fresh BLE `Capabilities` chain.
- Every canonical build must pass `scripts/check-engineering-policies.ps1` before a compiler starts. Do not bypass the gate; extend `docs/engineering-policy.json` when a new machine-checkable policy is adopted.
- The fixed text-only Android and firmware notice packs are integrity-checked using canonical LF line endings, not checkout bytes: preserve missing/extra-file and content-mismatch failures, update their manifests only through the reviewed repository verifiers/generator, and run the matching `scripts/test-*-release-notices.ps1` fixture when changing either verifier. Do not apply this text normalization to binary payloads.
- Before any Android or firmware compiler starts, the complete source change must be committed on a named branch and pushed to its configured upstream. Both canonical wrappers must run `scripts/assert-pushed-source.ps1`, which rejects dirty trees, detached commits, missing upstreams, and local or remote commit mismatches. Generated build outputs are disposable; source history is not.
- Treat app state, acknowledged device state, and cached capabilities as distinct. Reconcile only from fresh protocol evidence.
- Any UI state that implies X3 accepted a command must remain pending until a fresh protocol-ready link applies the reusable fast communication lease when needed and the matching X3 acknowledgement arrives. Persist and replay pending intent, but never present desired state as applied state.
- Treat valid USB commands as device activity: restore full-speed processing and extend the shared inactivity deadline for the bounded operation. USB workflows must not require a physical button press merely to leave low-power mode.
- Before diagnosing Android BLE scan/reconnect lifecycle, establish X3 power/transport presence first: check BLE advertisement/GATT and Pixel USB `connected/configured` after the standby interval; simultaneous absence is powered-off/physical absence until wake and lease reacquisition prove otherwise.
- For e-ink layouts, establish information hierarchy using size and position; do not rely on multiple gray shades for contrast.
- Before accepting any Android UI or X3 display-layout change, run the separate read-only Terra specialist roles in `docs/ui-specialist-review-contract.md`. One reviewer may not cover multiple required roles. Record passing evidence bound to the reviewed source hashes; `scripts/check-engineering-policies.ps1` must reject missing, reused, or stale receipts. Never replace these reviews with chat memory, a generic detector, compilation, or an uninspected screenshot update.
- Before implementing or reviewing UI, study `docs/ui-visual-language-foundations.md`. Do not accept an icon because it is merely visible or clickable: its metaphor, stroke geometry, negative space, placement, motion, and relationship to adjacent controls must pass the course rubric.
- Give UI reviewers compact source-and-evidence packets with `fork_turns: "none"`; never fork this long-running task history into a specialist. Check signed-in Codex usage before and after a reviewer wave, report a change of five percentage points or more, and stop optional review loops when less than twenty percent remains unless the user explicitly continues.
- Follow `docs/codex-usage-workflow.md` for signed-in meter checks, 30-minute checkpoints, forensic token accounting, model routing, delegation/build budgets, and mandatory dated ledger updates. Usage policy must live in the repository and engineering gate, never only in chat or model memory.
- Run `scripts/audit-codex-task-usage.ps1` once at task entry for observation and `scripts/audit-codex-task-usage.ps1 -EnforceStageGate` only before a compiler or device-deployment phase. The audit must bind to the invoking `CODEX_THREAD_ID`, falling back to `CODEX_SESSION_ID`; never use the newest rollout from another task or specialist. Replay, growth, and five-point task consumption are optimization signals: compact when the owning client can do so, shorten the next source-bound packet, and continue an already-bounded source fix in the same coordinator. They must not create a task cascade or block ordinary inspection, editing, focused tests, documentation, or correction of a discovered pre-build blocker. Only the protected-stage weekly reserve is fail-closed. Cache hits reduce computation but do not erase weekly usage.
- Keep one visible coordinator across related milestones. Do not automatically create a user-visible task or replace a working implementation owner. Use at most one internal `fork_turns: "none"` worker for sequential work; add parallel workers only for genuinely independent tasks. If the user explicitly requests a task transition, immediately navigate to and open that task in Codex. Status must state completed product work, the current phase, whether the phone or X3 changed, and the next verifiable outcome; omit worker mechanics unless asked.
- Route bounded work to the least expensive capable model: `gpt-5.6-luna` medium for discovery, logs, documentation, mechanical edits, focused tests, and build orchestration; Luna high for a bounded implementation with real cross-file reasoning; Luna xhigh only after a concrete medium/high reasoning failure or when a bounded failure is costly. Use `gpt-5.6-terra` medium/high for cross-layer state machines, firmware/device safety, unfamiliar weakly tested code, and the mandatory UI specialist roles. Sol remains the coordinator and is not a bulk execution worker. One owner takes a change through edit, focused verification, and checkpoint; do not pay another agent to repeat the same inspection.
- Bound every worker wait to at most ten minutes. When it expires, perform exactly one compact progress health check that verifies real evidence such as a new commit or working-tree change, an active build/deploy process, a device operation, or a concrete worker message. A `running` status alone is not progress. If evidence shows a real stall, interrupt and recover it; otherwise begin one new bounded wait. Do not repeatedly poll, nudge, or invoke the coordinator without a new event.
- Treat every acknowledged workflow mistake as a policy defect, not a chat-only apology. In the same checkpoint, update the durable workflow guidance and a machine-checkable rule or focused fixture when practical, and record the correction in the usage ledger. This self-correction rule applies recursively: failing to document a workflow mistake is itself a workflow mistake that must be documented and enforced.
- Agents own model routing, context compaction, known toolchain/path recovery, evidence-based retry, build sequencing, and other safe in-scope execution management. Do not delegate those decisions back to the user. Ask only for an unauthorized destructive action, unresolved irreversible target ambiguity, external credentials/coordination, meaningful scope expansion, or a genuinely product-changing choice.
- Before starting a Pixel-backed work phase, run `scripts/manage-pixel-screen-timeout.ps1 -Action Begin`: it snapshots the current timeout and disables automatic screen-off without overwriting an existing snapshot. At every completion, stop, or error checkpoint, run the same script with `-Action Restore` to restore the exact saved value. If state is missing or restoration fails, apply the 30-minute fallback. Never leave a diagnostic/build/deploy task with an unbounded Pixel timeout.
- Before every substantial milestone implementation, run a bounded regression-impact audit against the relevant power, synchronization, pairing, state-truth, and legal policies plus measured hardware evidence. Treat measured behavior as a constraint: if a proposed fix conflicts, document an explicit compatibility decision backed by evidence before editing; never silently regress a policy or replace measurements with assumptions. At the milestone checkpoint, update `TODO.md` status and normalize the result and remaining backlog in the directly relevant current `HANDOFF.md` section. Continue the next related milestone in the same coordinator unless the user explicitly asks for a new task.
